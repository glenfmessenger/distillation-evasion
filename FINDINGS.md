## F13 — 2026-11-10 — D8 as Jensen–Shannon divergence carries a sample-size bias with the wrong sign
An unpublished but measured repo (lodetomasi/model-extraction, docs/related.md) found JSD between an identity's distribution and the benign population is *anti-correlated* with attack: a concentrated campaign estimates its own distribution better than a sparse benign user, so its divergence is lower. It also found diverse benign users cover more cells than a focused campaign. Both apply to PROTOCOL §5 D8 as drafted. Pre-registering D8 as JSD without a sample-size correction risks a detector that fires on benign exploration. Feeds D-6 (new option) and TtV T10.

## F38 — 2026-11-11 — DEFECT in my own verifier: the math-verification timeout could not fire, and the pilot repair run stalled for 2 h 10 min at step 177 of 200 (rescued in place; verifier rewritten)
Source: /home/ubuntu/data/logs/grpo_pilot_s0.log (last write 10:15:42 UTC, next write 12:29:10 UTC); stack sample taken on the node at 12:27 UTC. The F17 fix ran math-verify in a thread pool and enforced the budget with `future.result(timeout=20)`. A generated answer made sympy evaluate a tower of powers (`Integer._eval_power` inside `simplify`), which is a single big-integer multiplication in C that never releases the interpreter lock. The main thread's timeout therefore could not wake, the trainer hung with the GPU idle, and the process grew to 392 GB resident (of 442 GB on the node). The timeout was a check that could not fail in exactly the case it existed for (global rule 3).
- Rescue: attached gdb to the live trainer and forced the innermost multiplication frame in the worker thread to return a null result, which CPython treats as an allocation failure. Memory fell to 10 GB and training resumed at step 178. No library file on disk was touched. The affected completion was scored as a timeout (reward 0, counted in `reward_fn.timeouts`), which is the designed outcome for a verification that exceeds its budget. One of 128 completions in one of 200 steps.
- Consequence for the record: the pilot repair's wall time includes a 2 h 13 min stall that is not training cost; F30's per-step cost stands. The remaining steps of this run still use the old in-memory verifier and can stall again; it is being watched.
- Exposure of earlier numbers: every scoring run so far (F28, F34) used the same thread-based verifier. A stall there would have hung the run rather than produced a wrong score, and all of those runs completed, so no reported number is affected.
- Fix (this commit): math verification now runs in killable worker processes (`dev_harness.math_worker`) with a wall-clock budget and, on Linux, an 8 GB address-space limit; a worker that exceeds either is killed and the caller gets `VerifyTimeout` (an error row, never a silent 0). Regression test: `test_math_verification_blowup_is_killed_and_the_pool_recovers` feeds a tower of powers and requires the raise within budget and a correct answer on the next call.
- Not yet known: whether math-verify swallows a `MemoryError` internally and returns "not equal" before the worker can report it. If it does, a memory-limited comparison is scored 0 instead of an error. Bounded by the count of such items; to be checked against the error rows of the after-repair scoring.
